## 1. Scope completed

No Phase 1 normalized import model, commit pipeline, clipboard refactor, or editable PPTX importer is included in this phase.

## 2. Existing architecture map

### 2.1 Editor and clipboard

- `StudioElement` is the persisted editor object model in `frontend/src/features/teaching-studio/types.ts`.
- `TeachingStudioPage.tsx` currently owns native and external clipboard event handling, element placement, selection, undo history, and dirty-state updates.
- Native Spectropy copies use `application/x-spectropy-studio-elements` plus `text/html` and `text/plain` fallbacks.
- Native paste supports destination-theme, source-formatting, picture, and text-only modes through `studioClipboardModel`.
- One paste operation commits one editor-history entry through the existing element commit path.
- External paste currently handles files, images, HTML, and plain text, but representation choice is distributed in the page component and does not yet use the shared import architecture.
- The asynchronous toolbar copy path currently writes HTML and plain text but not the Spectropy custom representation. This is a Phase 2 gap, not a Phase 0 change.

### 2.2 Contextual formatting

- Contextual tabs are selected from the active element type by the existing ribbon model.
- Image elements activate Picture Format; media, 3D, shape, and text objects retain their existing contextual tabs.
- Phase 2 must preserve this behavior for pasted external content.

### 2.3 Resource and persistence flow

- Resource uploads and versions are persisted through the existing Resource Library services and storage abstraction.
- Existing resource package inspection already checks traversal, symlinks, extensions, entry counts, entry sizes, expanded size, and compression ratios.
- Screen saves use revision checks and a database transaction for one screen plus its resource mappings.
- The current API has no atomic multi-screen/multi-resource import transaction. Phase 1 must introduce a staged plan and verified cleanup/compensation boundary instead of bypassing current services.
- The generic Resource Library upload limit remains unchanged; the PPTX importer will use the stricter import-specific limits in Section 6.

## 4. Fixture inventory and evidence

The deterministic synthetic fixture is generated by the backend test. Large or proprietary acceptance decks are not copied into the repository; their SHA-256 identities and expected traits are recorded in `backend/tests/fixtures/pptx-import/fixture-manifest.json`.

Representative evidence:

- Trigonometry: 19 slides, 140 ZIP entries, editable shape/text structure, groups, connectors, notes, images, and slide timing.
- Quadratic equations: 18 slides, text/shape-heavy, 925 shapes, 1,210 text runs, notes and timing on every slide.
- Heat transfer: 7 slides, image-heavy, multiple masters/layouts/themes, groups, connectors, and timing.
- SMART-ENT: 13 slides, high shape density, grouped content, SVG/PNG/JPEG assets.
- Two Biology packages contain encrypted ZIP entries and are explicit rejection fixtures requiring a password-free `.pptx` copy.

The safe inspector reads package metadata and XML only. It does not execute macros, ActiveX, embedded objects, or package content.

## 5. Architecture decision

### Decision: hybrid browser/backend import architecture

1. The browser owns clipboard acquisition, representation inventory, user paste options, placement, and current-editor interaction.
2. The backend owns PPTX upload validation, ZIP safety enforcement, Open XML relationship resolution, structural parsing, import preflight, resource planning, and import-job orchestration.
3. Both adapters produce the shared normalized import contract defined in the approved specification.
4. The frontend commits clipboard imports through existing editor boundaries. PPTX import uses a backend staged transaction/compensation workflow because it can create multiple screens and resources.

### Evidence

- Browsers alone can access clipboard representations but cannot recover editable PowerPoint structure when the source exposes only a rendered image.
- The backend already owns authentication, resource storage, ZIP/XML libraries, package safety controls, database transactions, and cleanup responsibilities.
- Representative decks range from less than 1 MB to approximately 47 MB and contain hundreds or thousands of objects. Parsing them in the React render path would risk UI blocking and duplicate security logic.
- Encrypted entries and malicious package limits must be rejected before parsing or resource creation.

This decision replaces the earlier open frontend-only versus backend-assisted question.

## 6. Initial operational limits

These limits apply to the editable PPTX import endpoint, are configurable, and will be benchmarked again during Phase 3:

| Limit | Initial value |
|---|---:|
| Accepted format | Password-free `.pptx` only |
| Rejected formats | `.ppt`, `.pptm`, encrypted/password-protected packages |
| Compressed upload size | 100 MB |
| Slides per import | 100 |
| ZIP entries | 5,000 |
| Total uncompressed size | 500 MB |
| Single ZIP entry | 50 MB |
| Single media asset | 50 MB |
| Maximum compression ratio | 200:1 |
| Preflight/inspection timeout | 60 seconds |
| Import job timeout | 5 minutes |

The importer must reject violations before persistent content is created and return a stable issue code plus a user-readable explanation.

## 7. Confirmed product defaults

- PPTX import creates new screens and does not overwrite existing screens in the MVP.
- Source formatting is the default.
- Slides fit proportionally to the Spectropy canvas while preserving relative layout.
- Unsupported visible objects use an explicit picture fallback when safe and are listed in the report.
- PowerPoint animation conversion is deferred to the approved teaching-content phase.
- Native editable PowerPoint export and legacy `.ppt` import are outside the MVP.
- The original PPTX is not retained after processing unless a later storage/privacy decision explicitly permits it.
- The supplied Trigonometry deck is a mandatory acceptance fixture.

## 8. Clipboard representation baseline

| Source | Representations currently verified | Current outcome |
|---|---|---|
| Spectropy event copy | Custom Spectropy MIME, HTML, plain text | Exact internal editable copy when the custom representation is available. |
| Spectropy async toolbar copy | HTML, plain text | Loses the custom representation; Phase 2 must align it. |
| External files/images | Browser file/image items | Image/resource insertion path. |
| External rich text | HTML and plain text when exposed by the browser | Existing HTML/text conversion with limited structure. |
| PowerPoint multi-object selection | Browser-dependent; observed image fallback can flatten objects | Use the best safe representation; direct users to PPTX import for reliable editable reconstruction. |

Phase 2 must inspect all available `DataTransfer` representations before choosing one, preserve the native custom MIME path, and record Chrome/Edge end-to-end observations for every supported source class.

## 9. Risks and deferred work

- Rich external clipboard content remains representation-dependent until Phase 2.
- Full PPTX parsing, inheritance, conversion, resource commit, UI progress, and rollback belong to Phases 1–3.
- Visual fidelity budgets require normalized rendering and reference comparisons in Phase 3.
- Charts, SmartArt, 3D, embedded media, advanced animations, and malicious-package fixtures expand in Phases 3–5.
- Repository-wide lint debt is pre-existing; phase gates use passing targeted lint/tests plus build until the general baseline is separately remediated.
